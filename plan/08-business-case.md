# 08 · 商业评审：市场、单位经济、增长、法务

> 这份文档是从"准备投钱的人"的角度对 `PRODUCTIZATION.md` 与 `plan/01–07` 的补充。前七份文档回答"怎么建"，几乎没有回答"为什么有人付钱、能赚多少、用户从哪来、哪些外部义务会咬人"。下文所有数字都是**带假设的估算**，标 ⚠ 的是需要你拍板的事项，已同步登记到 `README.md` 的决策门。

## 0. 一段话总评

技术方案扎实，风险识别到位（预扣结算、幂等、隐私披露、审核测试账号这些坑都提前看到了），工程上没有明显的架构性错误。**短板全在商业面**：没有竞品与定位、没有单位经济模型、没有获客计划、没有每个里程碑的量化放行标准、没有把税务与开源许可这两个会实际咬人的外部义务纳入。另外有几处技术细节会在上线当天出问题（`launchWebAuthFlow` 从 popup 调用、全局预算单例 DO 在热路径上、免费额度买不起一次测验），已直接修进对应文档。

按现在的方案，这是一个**独立开发者可持续经营的小生意**（几百到一两千个付费用户、月净收入几千美元量级），不是风投意义上的项目。这不是贬义：成本结构极轻（无人力、无固定服务器），到 100 个付费用户就能覆盖全部运营成本。但如果目标是更大的盘子，必须回答"分发渠道是什么"，这个问题目前是空白。

## 1. 目标用户

**理想用户画像（ICP）**：正在读日文原生内容（新闻、小说、推文、游戏 wiki、工作邮件）的 **N4–N2 学习者**。理由：

- N5 以下即使有振假名也读不懂句子，主要痛点是词汇量，不是"读网页"。
- N1 以上很少需要振假名，翻译需求转向专业内容，价格敏感度低但人数少。
- N4–N2 是"能读但吃力"的区间，也是学习者数量最大、坚持时间最长（通常 1–3 年）、对工具付费意愿最高的阶段。`jlptLevel` 设置默认 N3 与此一致。

**次级人群**：在日外国人（工作邮件、行政文书、租房合同），需求是"读懂"而非"学习"，对翻译与 TTS 的依赖更高，对付费不敏感；教日语的老师（团队/教育版的入口，M4）。

**规模参考**（数量级，来源为公开数据，实施前核实当年数字）：JLPT 全球年报名约 150 万人次；Duolingo 日语课程学习者数千万；r/LearnJapanese 订阅数百万量级。取"每年活跃、在桌面浏览器上读日文、愿意装扩展"的交集，可触达人群按 **数十万** 估。Chrome 扩展在 Education 类目里 10 万安装已是头部。

**地域**：`_locales` 已覆盖 vi / th / id / ms / my / ne / fil / si 等东南亚与南亚语言，说明产品事实上面向的是全球日语学习者，其中相当比例在**中低收入国家**。这直接影响定价（§4）与支付渠道（§7）。

## 2. 竞品与差异化

| 产品 | 形态 | 价格 | 强项 | 对比 Yomeru |
|---|---|---|---|---|
| Yomitan（原 Yomichan） | 扩展，离线词典弹窗 | 免费开源 | 社区巨大、零延迟、离线、词典生态 | 词典查词不看上下文（多音字/送假名歧义靠用户自己判断），无整句翻译、无语法讲解、无高质量 TTS。**是最大的心智竞争者**：用户第一反应是"我已经有 Yomitan 了" |
| 10ten Reader / Rikaikun | 扩展，词典弹窗 | 免费 | 轻量 | 同上 |
| Immersive Translate（沉浸式翻译） | 扩展，双语对照翻译 | Pro 约 $7/月，另有 BYO key | 用户量极大、中文用户主场、多引擎 | 定位是"翻译"不是"学习"：无振假名、无语法、无词汇本/测验。但它证明了"扩展 + BYO key + 订阅"这条路能走通 |
| Migaku | 扩展 + App，沉浸学习 | 约 $10/月 | 日语解析、SRS、视频字幕整合 | **最接近的付费竞品**。功能更重、学习曲线陡；Yomeru 的优势是"任意网页、选中即用、零配置" |
| Language Reactor | 扩展，Netflix/YouTube 字幕 | Pro 约 $5–8/月 | 视频场景 | 场景不同，可互补 |
| LingQ / Satori Reader / Todai | App，精选内容阅读 | $9–13/月 | 内容与分级 | 封闭内容库 vs Yomeru 的开放网页 |

（价格为撰写时的大致水平，标 ⚠ 核实。）

**差异化必须一句话讲清，并出现在商店描述第一行**：

> Yomitan 告诉你这个词是什么；Yomeru 告诉你这句话在说什么。

具体支撑：LLM 按上下文给读音（「生」「行」「日」在不同语境的正确读法是词典做不到的）；同一次选择同时拿到读音、译文、语法；阅读器把整篇文章变成带持久化的学习材料；朗读用的是自然语音而非系统 TTS。**BYO key 路径是信任资产**：隐私敏感用户可以选择文本完全不经过我们的服务器，这一点 Migaku 与 Immersive Translate 的托管模式给不了。

**弱点要诚实**：在线、有延迟、有成本；对已经习惯 Yomitan 的重度用户吸引力有限。目标不是替代 Yomitan，而是与之共存（很多用户会两个都装）。商店描述里不要攻击 Yomitan。

## 3. 价值阶梯 ⚠

`05` §1.3 给了 Free / Pro / 加油包三档，但**没有说明 Pro 除了"更多 credits"还多什么**。用户为订阅付钱通常需要一个质的差异，不只是量的差异。

现有成本模型下（`05` §1.2）的一个隐藏问题：语法与测验默认走中档模型，单次 70 / 240 credits，而免费档每日只发 200 credits。**免费用户一天做不了一次测验，语法分析只能做 2 次**，这两个功能在免费档事实上不存在，而它们恰恰是与 Yomitan 拉开差距的功能。

建议的阶梯（待确认）：

| | Free | Pro |
|---|---|---|
| 标注 / 翻译 | flash 档，每日额度 | flash 档，月额度 |
| 语法 / 测验 | **flash 档**（7 / 24 credits，免费档能用） | **中档**（更准确的讲解） |
| 朗读 | 每日约 5 分钟 | 月额度内不限，含更多音色 |
| 阅读会话云同步（M4） | 否 | 是 |
| 模型选择 | 无 | "高质量"开关（中档，按倍率扣） |

这样 Pro 的叙事是"更准的语法讲解 + 不限量的朗读 + 跨设备"，而不是"多 250 倍额度"。

## 4. 单位经济模型

所有价格沿用 `05` §1.2 的示意假设（flash 档 $0.10 / $0.40 每 M tokens，TTS $15 / M 字符）。

### 4.1 每个 Pro 用户

| 项 | 金额 | 说明 |
|---|---|---|
| 标价 | $7.99 | |
| Stripe 直连手续费 | −$0.53 至 −$0.70 | 2.9% + $0.30；国际卡 +1.5%，货币转换 +1%，Stripe Tax +0.5% |
| MoR（Paddle / Lemon Squeezy / Polar）手续费 | −$0.90 | 约 5% + $0.50，**含税务合规与拒付处理** |
| 到手 | **约 $7.10–7.45** | 两种通道对海外用户差距不到 $0.3 |
| 上游成本：轻度（每周 2 篇，不朗读） | −$0.20 | |
| 上游成本：典型（每天 1 篇，一半朗读） | −$1.50 | |
| 上游成本：重度（打满 50,000 credits） | −$5.00 | 额度上限即成本上限 |
| **毛利** | **典型 ≈ $5.7（78%）；最差 ≈ $2.2（30%）** | |

结论：Pro 定价的安全边际来自"月额度上限 = 成本上限"，这个设计是对的。**千万不要做"不限量"档位**。

### 4.2 每个免费用户

| 场景 | 月成本 |
|---|---|
| 每天打满 200 credits | $0.60 |
| 典型（每月 10 个活跃日，每日用 60%） | $0.12 |
| 只装不用 | $0 |

### 4.3 盈亏平衡

一个典型 Pro 用户的毛利（$5.7）可以补贴 **约 47 个典型免费用户**，或 **约 9 个打满的免费用户**。换算成"付费用户 / 免费活跃用户"的转化率要求：

| 免费用户行为 | 需要的转化率 |
|---|---|
| 典型 | ≥ 2.1% |
| 全部打满 | ≥ 10.5% |

Freemium 工具类产品的典型转化率是 2–5%。**模型成立的前提是免费用户的平均消耗接近"典型"而非"打满"**，每日发放而非注册赠送的设计正是为了压住这个平均值。`GLOBAL_DAILY_BUDGET_USD = 15` 对应每天最多 750 个打满的免费用户或约 3,750 个典型免费月活；这个数字必须随付费收入等比放大，否则会变成增长的天花板（用户在高峰期看到"今日服务繁忙"就会卸载）。

### 4.4 固定成本与规模刻度

| 项 | 月费 |
|---|---|
| Cloudflare Workers Paid | $5 |
| 域名 | ~$2 |
| 支付通道 | 0（按交易） |
| 收款主体维护（若走 Stripe Atlas 美国 LLC：注册 $500 一次 + 年税务申报与注册代理约 $1,000–2,000） | 折合 $100–200 |
| 收款主体维护（若走 MoR，以个人身份） | $0 |
| **M2 免费窗口的上游敞口** | 上限 = `GLOBAL_DAILY_BUDGET_USD × 30`，初始 $450 |

| 规模 | 月净收入（典型消耗） | 需要的免费月活（3% 转化） | 大致安装量（30% 安装→月活） |
|---|---|---|---|
| 100 Pro | ≈ $570 | 3,300 | 11,000 |
| 500 Pro | ≈ $2,850 | 16,700 | 55,000 |
| 1,000 Pro | ≈ $5,700 | 33,000 | 110,000 |

10 万安装在 Chrome 商店 Education 类目里已属头部。**没有分发策略，这张表的后两行到不了。**

### 4.5 定价本地化 ⚠

$7.99 对越南、尼泊尔、缅甸、印尼用户约等于当地一顿以上正餐，而这些正是 `_locales` 已覆盖的市场。两个选项：

1. Stripe 多币种价格 + 按国家的 PPP 折扣（Stripe 支持按国家设定不同 Price，Checkout 自动匹配）；MoR 通道通常也支持。
2. 首版只做 USD 单价，观察各国转化后再补。

建议选 1 的简化版：USD 单价 + 3–4 个重点低收入市场的折扣价（如 $3.99），因为这些市场的用户上游成本与其他市场一样，边际利润仍为正。风险是 VPN 套利，靠支付卡国家判断即可。

## 5. 增长与获客

计划里唯一的获客动作是"上架"。Chrome 商店的自然搜索流量对新扩展很小，必须有主动渠道。

### 5.1 上线（M0 公开后 2 周内）

- **Show HN / Product Hunt**：叙事是"开源、BYO key、文本不经过任何第三方服务器的日语阅读扩展"，这个角度在 HN 有天然受众。
- **r/LearnJapanese、r/japanese、r/LanguageLearning**：注意各版的自我推广规则（通常要求先参与、按比例发帖）。用"我做了这个工具，求反馈"而不是广告口吻。
- **日语学习 Discord 服务器**（多个万人级社区）、X / Bluesky 上的日语学习圈。
- **中文渠道**（BYO key 路径在大陆可用）：少数派、V2EX、B 站、小红书。注意这批用户的托管付费路径要等决策门 1。
- **YouTube 小型日语学习创作者**（1–10 万订阅）：免费给 Pro 一年换一期视频，成本几乎为零。

### 5.2 持续（M2 起）

- **SEO**：`docs/` 已有 18 语言落地页，这是现成资产。补齐意图明确的页面：「NHK Easy 加振假名」「青空文库阅读器」「Yomitan vs Yomeru」「怎样给任意网页加 furigana」。
- **产品内传播**：把标注好的句子导出为图片卡片（ruby + 译文 + 品牌角标），用户发推/发朋友圈时带来曝光。成本一天。
- **推荐奖励（M3 后）**：被推荐人**首次付费**时双方各得 credits。不要在注册时就发，否则又回到"薅羊毛"问题。
- **留存**：引导页（`01` §1.4）、词汇本间隔重复（M4）、每周学习摘要邮件（M4）。留存是所有转化率的分母，比拉新更重要。

### 5.3 M0 的信号失真

M0 是 BYO key 形态，用户必须先去 OpenAI 申请 key。**这会把用户筛选成"愿意折腾 API key 的技术型学习者"**，他们的留存、评价、功能偏好都不能代表大众市场。M0 拿到的数据用来验证"产品本身有没有人要"是够的，用来推算 M2 之后的注册转化率是不够的，排期与预期要按这个理解来定。

## 6. 指标与决策门 ⚠

现有计划说"先拿到真实用户与数据再决定值不值得建后端"，但没有定义"值得"的数字。以下是建议的放行标准（数字待确认）：

### M0 → M2（公开 4 周后评估）

| 指标 | 放行 | 数据来源 |
|---|---|---|
| 累计安装 | ≥ 300 | 商店后台 |
| 周活 / 安装 | ≥ 30% | 商店后台 |
| 评分 | ≥ 4.3（≥ 10 条评价） | 商店后台 |
| 卸载调查中"配 API key 太麻烦"占比 | ≥ 30%（验证托管额度是真需求） | `setUninstallURL` 问卷（已加入 `01` §1.4） |
| 不放行 | 4 周 < 100 安装且无增长趋势 → 先解决分发，不建后端 | |

M0 按隐私政策**没有任何遥测**，可用的只有商店后台统计、卸载问卷、GitHub Issues 与评论。够用，不要为了数据加埋点。

### M2 → M3（免费托管上线 4 周后）

| 指标 | 放行 |
|---|---|
| 新安装 7 天内登录率 | ≥ 25% |
| 登录用户 D7 留存 | ≥ 25% |
| 活跃用户日均上游成本中位数 | ≤ $0.02（模型假设成立） |
| 每周 ≥ 3 天触顶每日额度的用户占比 | ≥ 10%（存在付费需求） |
| 单用户熔断触发 | 每周 < 5 次（滥用可控） |

### M3 成功标准（收费 60 天后）

免费→Pro 转化 ≥ 2%；月流失 ≤ 8%；毛利率 ≥ 65%；退款率 ≤ 3%。任一严重不达标即回到 §3 重新设计阶梯，而不是继续做 M4。

## 7. 法务、税务与收款主体 ⚠

这一节是现有计划里缺口最大、且**不做会直接违规**的部分。

### 7.1 收款通道：Stripe 直连 vs Merchant of Record

`PRODUCTIZATION.md` 已决定 Stripe，但决定时没有把税务义务算进去。关键事实：

- **欧盟**：非欧盟主体向欧盟消费者销售数字服务，**从第一笔起**就要按买家所在国缴 VAT（€10,000 门槛只适用于欧盟内主体），需通过 Non-Union OSS 登记季度申报。Stripe Tax 能算税，但**登记与申报是你自己的事**。
- **英国**：同样从第一笔起需登记 UK VAT。
- **日本**：消费税对海外数字服务提供者有登记门槛（约 ¥1,000 万应税销售额），初期可不管，但在日用户是本产品的自然人群，要盯。
- **美国**：各州经济关联门槛（多为 $100k 或 200 笔），初期不触发。
- **拒付**：每笔争议 $15 手续费，且拒付率超过阈值会被 Stripe 风控。

| | Stripe 直连 | MoR（Paddle / Lemon Squeezy / Polar） |
|---|---|---|
| 费率 | 2.9% + $0.30，国际另加 | 约 5% + $0.50 |
| 税务 | 自己登记、申报 OSS / UK VAT / 各州 | MoR 是法律意义上的卖家，全部由其处理 |
| 拒付 | 自己处理，$15 / 笔 | MoR 处理 |
| 收款主体 | 需要 Stripe 支持地区的实体 | 多数支持以个人身份签约，通过 PayPal / Payoneer / 银行电汇打款 |
| 与本方案的契合 | `05` §6 按 Stripe 写 | webhook 事件不同，但账本设计（`ledger.ref` = 支付方事件 ID）是通道无关的，改造量约 2–3 天 |
| 适合 | 月收入 > $10k 后、有会计支持时 | 单人、全球 B2C、初期 |

对海外用户，两条通道到手金额相差不到 $0.3（§4.1），而 MoR 免掉了全部税务登记与申报。**从投资人角度，单人项目在月收入 $10k 以下选 MoR 几乎是无条件的**；`07` 把 MoR 列为"备选"低估了它。这与"收款主体在哪"（决策门 2）绑定，请一起决定。

### 7.2 Chrome 商店的 trader 声明（欧盟 DSA）

商店后台要求开发者声明是否为 **trader**。一旦开始收费就是 trader，须提供并**公开展示**联系地址、邮箱、电话，且 Google 会验证。这意味着：

- M0 / M2 可按非 trader 提交；**M3 上线前必须切换为 trader 并通过验证**，否则 listing 会被下架。
- 个人开发者需要一个可公开的地址（虚拟办公室 / 邮箱服务），提前办理。
- 若走 MoR，MoR 是卖家，trader 信息如何填写需向平台确认。

已加入 `06` §5 与 `07` 的 M3 任务。

### 7.3 隐私与数据保护

在 `04` §5 的隐私政策 v2 之外还缺：

- **子处理者清单**：OpenAI、Anthropic、Google、ElevenLabs、Cloudflare、支付方。GDPR 要求可查。
- **上游数据使用条款**：三家 API 默认不用 API 数据训练，但 **Gemini API 的免费层会用于训练，只有付费层不会**。托管模式必须用付费层，隐私政策"不用于训练"的陈述才成立。已加入 `03` §6。
- **GDPR 第 27 条欧盟代表**：欧盟外主体常规处理欧盟居民数据时原则上需指定，小规模、低风险处理有豁免空间。⚠ 需在有欧盟付费用户前评估。
- **日本 APPI**：面向日本居民提供服务的海外经营者适用，义务较轻（告知目的、安全措施、跨境传输说明），隐私政策写清即可。
- **数据可携**：词汇本与阅读会话已在本地可导出；账号数据（用量）导出已在 `04` §5。

### 7.4 开源许可与仓库公开 ⚠

`README.md` 声明 MIT，但**仓库里没有 LICENSE 文件**，法律上许可状态是含糊的；同时 `github.com/darmau/kana-master` 是**公开仓库**。计划把 `server/`（计费逻辑、防滥用规则、prompt、对账）放进同一仓库，等于把 SaaS 后端全部开源。

三个选项：

1. **整个仓库转私有**。最省事，失去"开源、可审计"这张信任牌，且已公开的历史无法收回。
2. **扩展保持 MIT 公开，`server/` 另建私有仓库**。推翻 `03` §2 的单仓库决定，协议变更要跨仓库 PR；共享的 `lib/prompts.js` 需要以 git submodule 或复制方式同步。
3. **单仓库公开，扩展 MIT、`server/` 用 source-available 许可**（如 FSL / BUSL：可读可自用，禁止商业竞争性托管）。保留信任资产与单仓库便利，代价是法律文本多一份、部分人不认这类许可。

无论选哪个，**M0 上架前先补 LICENSE 文件**（现在的状态对任何贡献者和用户都是不利的）。若沿用 MIT，要接受他人可以原样改名重新上架（商店有冒充政策可投诉，但不能事前阻止）。

### 7.5 品牌与商标 ⚠

- **"Rubify" 与 "Yomeru" 商标检索**：至少查 USPTO、EUIPO、J-PlatPat 的第 9 / 42 类，以及 npm / RubyGems / 商店里的同名产品。域名可注册不等于名字可用。
- **双品牌的转化代价**：用户装的是 Yomeru，登录弹窗、账单、支持邮箱看到的是 Rubify。对不了解背景的用户，"用 Google 登录 Rubify"出现在一个叫 Yomeru 的扩展里，观感接近钓鱼，会压低登录转化；Google 品牌验证也会核对同意屏幕应用名与主页是否一致。行业惯例是**产品一个名字，公司另一个名字并只出现在法律文本和账单抬头**（"Yomeru, by Rubify"），而不是让两个名字都面向用户。这条与上一次提交的决定相反，请重新确认。

### 7.6 服务条款要点（补充 `06` §5.2）

- 额度与价格可调整的保留条款（含提前通知期）。
- 拒付即暂停账号；负余额禁止托管请求（`05` §6.3 已有）。
- 未成年人：Google 账号本身要求 13 岁以上；服务条款写明 13+（或所在地法定年龄）。
- 管辖法与争议解决按收款主体所在地。
